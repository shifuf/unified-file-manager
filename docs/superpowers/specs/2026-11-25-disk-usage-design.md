# 统一文件管理磁盘占用优化

用户希望清理 Agent2API 升级残留，并查明、优化统一文件管理的 MySQL 和 Docker 空间。Agent2API 清理已另行完成：释放 10.48 GB，保留校验通过的最近一份完整备份，服务健康。

## 实测原因

- MySQL 数据卷约 11.35 GB，其中 binlog 约 11.06 GB；业务表目录约 74 MB。
- MySQL 使用 `binlog_row_image=FULL`，过期时间为 30 天。
- 抽样 17 MB binlog 中，约 16.97 MB 是 `ManagedFile` 更新。进一步比较 24 次更新，变化字段为 `storageKey`、`checksum`、`updatedAt` 和少量 `size`；未变化的 `contentText` 仍随整行写入，最大字段为 200 KB。
- 当前 API 镜像包含前端依赖，历史上存在约 617 MB 依赖 COPY 层和约 631 MB 递归 chown 层。

## Approaches

1. 只删除历史文件：立即释放空间，但不解决日志写入放大和镜像膨胀。
2. 拆分数据库大字段、重写文件更新流程：涉及迁移和现有功能，超出本次必要范围。
3. 调整行日志和保留策略、隔离运行时依赖、复制时设置属主：保留现有业务和数据库结构，直接解决已证实的原因。

采用方案 3。用户此前要求直接处理并同步服务器/GitHub；默认值和具体实现是本次工程判断，不声称用户逐项选择了参数。

## 设计与约束

- 继续启用 binlog；默认使用 `MINIMAL` 行日志，记录主键和实际变化字段。
- binlog 默认保留 259200 秒（3 天），单文件上限 67108864 字节（64 MiB），均可通过环境变量配置；需要完整行日志的部署可配置为 `FULL`。
- MySQL 永久配置以 Compose 启动参数为准；在线临时调整仅使用 `SET GLOBAL`。已有 `SET PERSIST` 值先记录，保存 SQL 快照及旧 binlog 归档后，只清除对应三项持久值，再重新创建 MySQL 并核对实际变量和持久化记录。
- 运行时从独立 Node 基础镜像构建，单独安装 API 的生产依赖；保留 Prisma 迁移 CLI、生成客户端、sharp、ffmpeg 和存储插件 SDK。
- 复制 API 运行文件时设置 node 属主，只调整新建的存储目录属主；不递归 chown 整个依赖目录。
- UFM 容器启用可配置的日志轮转，默认 10m × 3。
- 不改变文件、账号、存储绑定、云端同步、任务和备份业务；不删除业务表或文件对象。
- 在用户指定的 `F:\统一文件管理` 修改，保留原先已暂存的 WebDAV 计划变更。
- 版本保持 0.2.2，在现有 feature 分支提交本次文件；不创建 tag 或正式 Release。

## 验收

运行镜像验收必须实际加载 API/Prisma/SDK、处理图片、调用迁移 CLI 和 ffmpeg，确认 node 用户可写存储目录，确认前端及插件工作区依赖没有被带入 API。验证 Compose 配置和 MySQL 实际变量；运行项目现有测试、lint 与构建。部署后核对服务健康、配置/数据保留情况和磁盘占用。
